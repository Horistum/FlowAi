# Migration: Abstract Execution Topology Model

## Summary

v0.9.7.8 separates executable environment requirements from action capabilities, dependency ordering, continuity declarations and renderer layout. A target can represent every requested action and still be unable to execute the plan safely when its isolation, lifetime, persistence or propagation evidence is incomplete.

## Target Registry 3.1

Target Registry advances from `3.0` to `3.1`. Target Manifest remains `3.0`.

Every target now requires a `topology` section with one declaration for each dimension:

- `workflowScope`
- `branchIsolation`
- `attemptIsolation`
- `workflowLifetime`
- `suspendResume`
- `ephemeralWorkspace`
- `durableState`
- `valuePropagation`
- `workspacePropagation`
- `statePropagation`
- `failurePropagation`

Each declaration is `supported`, `partial`, `unsupported` or `unknown` and must have one profile-level evidence reference. Missing, duplicate and contradictory declarations are invalid registry evidence.

## Planning artifacts

Flow AST and ExecutionPlan `2.0` add `topologyRequirements`. The addition does not change their contract version.

Requirements are derived from canonical intent and concrete plan structure. Examples include:

- non-empty workflows require workflow scope and lifetime;
- parallel groups require branch isolation;
- retries require attempt isolation;
- approval nodes require suspend/resume capability;
- resolved workspace continuity requires ephemeral workspace persistence and workspace propagation;
- resolved state continuity requires durable state and state propagation;
- error handlers require failure propagation.

Consumers must preserve these requirements. Manually constructed plans cannot omit requirements that are re-derived from their nodes or dependency relations.

## Materialization behavior

Executable materialization requires an exact topology match. `partial`, `unsupported`, `unknown` and contradictory topology evidence block provider invocation. Diagnostic materialization may preserve the blockers but remains explicitly non-executable.

Action support, projection rules, task ordering and continuity resolution do not substitute for topology evidence.

## Test fixtures and custom targets

Custom targets and test fixtures must provide an explicit complete topology profile. There is no production default that silently marks every topology dimension supported. Tests may use the named `testTargetCapability` helper, whose evidence references are explicitly test-scoped.

## Reference behavior

The Jenkins checkout-and-build reference remains executable because its target profile matches the required workflow lifetime, workspace persistence and propagation. GitHub Actions remains blocked for that scenario because workspace propagation is explicitly unsupported. Tekton remains blocked where its current topology profile is incomplete.

## Unchanged boundaries

The implementation package remains `0.9.5`, the next package line remains `0.9.6`, the public standard remains `0.8.0`, Intent/AST/ExecutionPlan remain `2.0`, Target Manifest remains `3.0`, and no runtime executor or target-specific public Flow syntax is introduced.
