# v0.9.7.6 Universal Effect and State Transition Model Migration

## Scope

This migration applies to code that constructs, serializes, validates or consumes Flow AST and execution-plan action nodes.

The change is additive at the serialized contract boundary. Existing resource-only `effects` remain present, while typed `effectModel` evidence becomes the semantic authority.

## Execution-plan fields

Task and data-operation nodes may now carry:

```json
{
  "semanticCapability": "BUILD_IMAGE",
  "effectModel": [
    {
      "domain": "SOFTWARE_DELIVERY",
      "operation": "CREATE",
      "resource": "software.image",
      "transition": {
        "from": "ABSENT",
        "to": "PRESENT"
      },
      "external": true,
      "sourceCapability": "BUILD_IMAGE"
    }
  ],
  "effects": ["software.image"]
}
```

`effectModel` is authoritative semantic evidence. `effects` is a derived compatibility projection containing the distinct resource values from `effectModel`.

Consumers performing semantic analysis must use `effectModel`. Consumers that only display affected resource identities may continue reading `effects`.

## Operation semantics

State transitions are fixed by operation:

| Operation | Transition |
| --- | --- |
| `CREATE` | `ABSENT` to `PRESENT` |
| `UPDATE` | `PRESENT` to `PRESENT` |
| `DELETE` | `PRESENT` to `ABSENT` |
| `UPSERT` | `UNKNOWN` to `PRESENT` |
| `READ` | no transition |
| `EXECUTE` | no transition |
| `EMIT` | no transition |
| `UNKNOWN` | no transition |

Do not provide a different transition for an operation. Construction and materialization validation fail closed when operation and transition disagree.

Reconciliation capabilities use `UPSERT` when Core cannot know whether the resource already exists. Implementations must not rewrite `UPSERT` to `CREATE` or `UPDATE` merely because one target currently behaves that way.

## Canonical intent producers

Producers lowering standard intent must derive effects through `CanonicalIntentEffectAuthority`. Do not infer effects from:

- module names such as `docker`, `argocd` or `kubernetes`
- implementation action names
- target inventories
- renderer structure
- ordering or continuity relations

Equivalent intent must produce the same typed effects with no implementation inventory available, with a different inventory available, and with an explicit compatible binding.

## Module action producers

Module descriptors continue to expose implementation-owned effect buckets. `ModuleEffectCanonicalizer` converts those buckets to the shared typed model.

Because module effect identities do not declare a universal domain, converted module effects use `domain: UNKNOWN`. Do not derive semantic domains from strings such as `docker.image` or `kubernetes.resource`.

Known standard-capability actions must carry the canonical effects for that capability. Raw module effects remain appropriate only where no canonical standard capability owns the meaning.

## Materialization validation

The mandatory materialization authority now validates effect evidence before provider invocation. It rejects:

- a known semantic capability with missing `effectModel`
- canonical effects that were changed, omitted or duplicated
- an operation with an incompatible state transition
- a legacy `effects` list that does not equal the resource projection of `effectModel`
- known module effects that do not match the canonicalized module contract

Update hand-built execution-plan fixtures and integrations to construct effects from the canonical authority or module canonicalizer rather than copying resource strings manually.

## Serialization boundary

The serialized effect shape contains only:

- `domain`
- `operation`
- `resource`
- `transition`
- `external`
- `sourceCapability`

Core does not depend on serializer annotations. Derived convenience properties or implementation identities must not be added to the wire format without an explicit contract migration.

## Reference evidence

Regenerate committed snapshots through the production reference generator. Do not edit `flow-ast.json` or `execution-plan.json` manually.

The checkout-and-build executable reference must remain explicitly scoped to Jenkins until another target has independently certified equivalent execution evidence.

## Version boundary

This additive migration does not change package version `0.9.5`, next package line `0.9.6`, public standard version `0.8.0` or artifact contract version `2.0`.
