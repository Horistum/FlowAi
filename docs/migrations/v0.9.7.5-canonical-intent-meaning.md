# v0.9.7.5 Canonical Intent Meaning Migration

## Scope

This migration applies to module descriptors and intent documents that use explicit module bindings.

## Module descriptors

Actions used by Standard Intent steps must declare the standard capabilities they implement:

```yaml
actions:
  sync:
    kind: action
    implements: [DEPLOY, SYNC]
```

The values are names from `StandardCapability`. Unknown values fail canonical module loading. An action without a matching declaration cannot satisfy an explicit binding for that capability.

## Intent documents

An explicit `uses` declaration now requires an explicitly selected compatible system:

```yaml
systems:
  - name: delivery
    type: argocd

workflows:
  - name: deploy
    kind: DEPLOY
    steps:
      - id: deploy
        capability: DEPLOY
        uses: argocd.sync
        params:
          system: delivery
          app: billing
          target: production
```

`params.system` selects the binding system. Semantic parameters such as `target`, `environment`, `version`, `source` or `destination` retain their semantic meaning and never select a system implicitly.

## Unbound intent

A step without `uses` remains valid standard intent. It lowers to target-neutral standard semantic work and does not select a module based on available inventory. Add `uses` and `params.system` only when an explicit implementation binding is intended.

## Validation changes

Binding errors are reported separately from canonical meaning. Typical migration diagnostics include:

- `USES_REQUIRES_MODULE_ACTION`
- `BINDING_MODULE_UNKNOWN`
- `BINDING_ACTION_UNKNOWN`
- `BINDING_CAPABILITY_NOT_IMPLEMENTED`
- `EXPLICIT_BINDING_REQUIRES_SYSTEM`
- `UNKNOWN_INTENT_SYSTEM`
- `BINDING_SYSTEM_TYPE_MISMATCH`

Fix the binding declaration or remove it. Do not change the standard capability merely to match an implementation action.
