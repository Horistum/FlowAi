# Migration: Universal Control and Policy Requirements

## Summary

v0.9.7.7 separates control requirements, evidence and authorization decisions. Earlier consumers often inferred all three from a policy declaration, a `destructive` flag or a safety string. Those values remain inputs to the control model but no longer authorize work by themselves.

## New execution-plan fields

Flow AST and execution plans now expose:

- `controlRequirements`: target-neutral obligations
- `controlEvidence`: one explicit evidence record per requirement
- `controlDecision`: the decision derived from the evidence set

The change is additive within artifact contract version `2.0`.

## Evidence states

- `SATISFIED`: known evidence proves the requirement is represented
- `UNSATISFIED`: explicit evidence contradicts the requirement
- `UNKNOWN`: required evidence is absent or cannot be established
- `DYNAMIC`: the evidence must be evaluated or enforced later by declared capabilities

`UNKNOWN` and `UNSATISFIED` block materialization. `DYNAMIC` produces a `PENDING` decision and must list its enforcement capabilities. Only a fully satisfied assessment is `ALLOWED`.

## Approval migration

An approval policy declares an `APPROVAL` requirement. It is not evidence that an approval mechanism exists.

Provide one of the supported explicit mechanisms:

- an authored `APPROVE` intent step
- an approval node produced by lowering
- an explicit Flow safety declaration such as `requiresApproval`
- dynamic approval evidence with `approval.manual` and `condition.evaluate` requirements

The reference secret-rotation scenario now includes an explicit approval step before rotation.

## Manually constructed execution plans

Plans that use canonical capabilities or module actions with safety contracts must include the re-derived control requirements, exactly one evidence record per requirement and the matching derived decision. Omitting the assessment, forging a requirement or decision, duplicating evidence, or failing to require dynamic enforcement capabilities is invalid planning evidence.

Use the production intent-to-AST and planner pipeline whenever possible instead of manually assembling these fields.

## Compatibility facades

`MandatorySafetyPolicy` and `SafetyPolicyValidator` remain available as deprecated facades. They delegate to `CanonicalControlRequirementAuthority` and no longer define independent safety semantics.

## Unchanged boundaries

Control requirements do not imply semantic effects, ordering, continuity or execution topology. Target inventory and renderer layout do not define control meaning. Package version `0.9.5`, public standard version `0.8.0` and artifact contract version `2.0` remain unchanged.
