# Migration: Intent Lowering and Diagnostic Honesty

## Summary

v0.9.7.9 removes permissive intent parsing and silent lowering loss. A meaningful input is now preserved in canonical artifacts, transformed with explicit lowering evidence, or rejected with a stable path-aware diagnostic.

## Strict loader behavior

The public intent loader now rejects:

- unknown fields at any supported intent object boundary
- map, list, scalar or boolean values with the wrong shape
- non-string object keys
- unknown trigger, schedule, workflow, policy or capability enum values
- unsupported normalized value types
- empty `secret:`, `ref:` and `expr:` values
- duplicate configuration keys supplied through both nested `config` and inline system fields

Failures use `IntentSourceException` with `code`, `path`, `sourceName` and a concrete detail message. Consumers should use the code and path rather than matching the human-readable message.

## Equivalent source forms

Block-style YAML, flow-style YAML, JSON and normalized maps remain equivalent. The same semantic input must produce the same `IntentDocument`, canonical meaning and validation diagnostics regardless of source syntax.

## New artifact evidence

Flow AST metadata and ExecutionPlan now expose:

- `sourceIntent`, preserving source description, workflows, policy source, system purpose and failure declarations
- `loweringReport`, containing deterministic source-to-target lowering evidence
- source step identifiers and descriptions on task and approval nodes
- explicit binding metadata separate from semantic parameters
- declared outputs
- canonical structured default expressions

The legacy scalar input default remains populated only for string literals. Consumers that need exact values must use the canonical default expression.

## Newly rejected inputs

The following inputs previously risked silent loss and now fail validation:

- unknown parameters on non-`CUSTOM` capabilities
- multiple workflows that would be flattened into one execution sequence
- `failure.stopOnError=false`, which lacks a canonical error-handling representation
- policy types without a canonical lowering contract
- empty or duplicate declared output names

`CUSTOM` retains arbitrary non-binding parameters because its canonical contract explicitly preserves them.

## Manual execution plans

Plans carrying `sourceIntent` must carry a matching lowering report. Materialization requires contract version `1.0`, unique and well-formed evidence entries, and exact source-step coverage by task or approval nodes. Missing, duplicated, malformed or forged evidence blocks provider invocation.

Use the production intent loader, validator, intent-to-AST planner and Flow planner instead of constructing source metadata manually.

## Unchanged boundaries

Lowering evidence does not replace binding, effects, continuity, control or topology evidence. It proves representation honesty, not target readiness. Package version `0.9.5`, public standard version `0.8.0` and artifact contract version `2.0` remain unchanged.
