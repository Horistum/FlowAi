# v0.9.7.6 Universal Effect and State Transition Model

## Status

Completed.

## Objective

Represent resource observations and state transitions through one implementation-independent semantic model shared by the bounded software delivery, data transformation and infrastructure state-change domains.

## Implemented contract

- `CanonicalIntentEffectAuthority` derives typed effects from standard capabilities before implementation binding
- effect evidence identifies the semantic domain, operation, resource, optional state transition, externality and source capability
- `CREATE`, `UPDATE`, `DELETE` and `UPSERT` have fixed state-transition meanings
- `READ`, `EXECUTE`, `EMIT` and `UNKNOWN` do not invent state transitions
- reconciliation capabilities such as deploy, sync and restore use `UPSERT` because Core cannot assume that the target resource already exists
- AST action nodes and execution-plan task or data-operation nodes preserve the same typed effect evidence
- legacy string `effects` remain a derived resource projection for compatibility and are not an independent semantic authority
- module-owned effect buckets convert to the shared model with domain `UNKNOWN` rather than inferring universal meaning from implementation names
- the mandatory materialization authority re-derives canonical effects and rejects missing, duplicate, contradictory or forged evidence

## Bounded-domain evidence

The same operation and transition vocabulary covers:

- software delivery, including repository reads, builds, packages and image creation
- data transformation, including source reads, transformed outputs, backups and restores
- infrastructure state change, including provisioning, deployment reconciliation, secret rotation and deprovisioning

Conformance verifies that equivalent intent retains equivalent effect evidence across inventories and explicit bindings.

## Serialization boundary

The Core effect model has no serializer-framework dependency. Serialized execution-plan evidence contains only declared semantic fields. Convenience getters and implementation-oriented identities are not part of the wire contract.

## Compatibility and migration

Execution-plan nodes now expose `semanticCapability` and typed `effectModel` evidence. The historical `effects` list remains available as a derived list of resource identities. Producers must derive canonical effects through the shared authority. Consumers should use `effectModel` for semantic reasoning and treat `effects` only as compatibility evidence. The migration guide documents the additive fields and fail-closed validation rules.

## Reference evidence

Both committed reference snapshot directories were regenerated through the canonical production generator. The checkout-and-build scenario remains explicitly scoped to Jenkins and preserves the live executable reference proof. No target inventory or renderer layout defines semantic effects.
