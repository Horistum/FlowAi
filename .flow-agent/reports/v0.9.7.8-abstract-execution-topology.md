# v0.9.7.8 Abstract Execution Topology Model

## Status

Completed.

## Objective

Make executable readiness depend on matching target-neutral execution-topology requirements and target evidence rather than action support or renderer structure alone.

## Universal topology contract

The shared model covers four independent dimensions:

- isolation: workflow scope, parallel branch isolation and retry-attempt isolation;
- lifetime: workflow lifetime and suspend/resume behavior;
- persistence: ephemeral workspace and durable state;
- propagation: value, workspace, state and failure propagation.

Canonical intent derives inventory-independent requirements before implementation binding. Planning adds requirements implied by the concrete control-flow structure and resolved continuity relations. Ordering alone adds no persistence or propagation claim.

## Target evidence

Target Registry `3.1` requires every target to provide one evidence-backed support declaration for each topology kind. Missing, duplicate and contradictory declarations fail closed. Partial evidence remains non-executable because a degraded execution environment cannot prove an end-to-end plan.

Built-in target profiles intentionally differ. Jenkins provides the complete topology needed by the existing checkout-and-build reference. GitHub Actions explicitly lacks workspace propagation for that scenario. Tekton and other targets preserve partial or unsupported facts instead of receiving an invented universal profile.

## Mandatory authorization

`MandatoryMaterializationAuthority` re-derives minimum topology requirements from the plan, rejects omissions and obtains a target assessment from the canonical registry profile. Only `MATCHED` topology can authorize executable provider invocation. Diagnostic authorization preserves blockers without claiming readiness.

Action capability, dependency ordering, continuity resolution and renderer layout remain separate evidence and cannot authorize execution topology.

## Compatibility and migration

Flow AST and ExecutionPlan `2.0` add topology requirements without changing their version. Target Registry changes from `3.0` to `3.1`; Target Manifest remains `3.0`. Custom targets and test fixtures must provide explicit profiles. The migration is documented in `docs/migrations/v0.9.7.8-abstract-execution-topology.md`.

## Reference evidence
