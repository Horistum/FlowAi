# v0.9.7.9.5 Provider-Backed Approval and Topology Identity

## Status

Implementation complete. Exact-head Flow CI validation is required before review readiness and is recorded on the pull request review surface.

## Confirmed failures

- `ApprovalNode` was unconditionally labeled `NATIVE` during target lowering even when no provider payload existed.
- Jenkins rendered approval from `step.type == approval` instead of a provider-owned payload contract.
- GitHub Actions job metadata could look like approval implementation evidence even though no step payload contract existed.
- Canonical control requirements were accumulated in a map keyed by lossy slug ids, silently overwriting distinct obligations.
- Canonical and planning topology requirements used lossy slug ids followed by `distinctBy`, silently discarding distinct subjects.

## Implemented design

Native approval is now a target-edge claim. `TargetNativeApprovalProjectionDefinition` declares the semantic approval capability, opaque renderer kind/reference, explicit provider evidence and the allowed semantic binding fields. `TargetNativeProjectionCatalog.compileApproval` resolves those fields into validated typed `LITERAL` bindings.

Jenkins declares one concrete `approval.manual` implementation backed by `JENKINS_STEP/input`. The Jenkins renderer validates that exact provider-owned payload before emitting `input message`. A provider without this contract receives `ADAPTER_REQUIRED`; capability metadata alone cannot create native materialization.

GitHub Actions intentionally receives no fake approval-step contract. Its protected-environment model is job-level topology and remains review-only until a provider contract can represent placement and environment protection honestly.

## Identity model

`CollisionSafeIdentityAuthority` keeps ordinary readable ids unchanged. When distinct semantic identities collapse to the same readable slug, every colliding member receives a deterministic twelve-character SHA-256 suffix derived from length-prefixed original components.

Control requirements include kind, unsanitized subject, source, condition and message in their semantic identity. Exact duplicate control obligations are rejected. Topology identity uses kind and the original subject; duplicate observations of the same topology meaning coalesce while distinct subjects remain present.

## Verification coverage

Tests and conformance cover:

- Jenkins approval requires a provider-owned `input` payload
- missing provider contract produces `ADAPTER_REQUIRED`
- GitHub capability or job metadata does not forge approval payload evidence
- native approval without a renderer payload remains review-only
- duplicate provider approval capabilities and duplicate semantic field mappings are rejected
- control subjects with colliding slugs retain distinct deterministic ids
- topology subjects with colliding slugs retain distinct deterministic ids
- canonical and planning observations of the same topology requirement coalesce
- ordinary non-colliding ids remain unchanged
- the Jenkins reference review snapshot exposes concrete approval payload evidence

## Architecture boundary

The change does not move target vocabulary into Core intent or planning. Semantic approval remains target-neutral. Only the composed edge provider owns the target payload and renderer reference. No plugin discovery, command transport, shell projection or optimistic fallback is introduced.

## Build discipline

Repository changes are assembled on a branch before the pull request is opened. The standard full Flow CI run is triggered only for the complete candidate head. A subsequent run is allowed only when the first run exposes a concrete defect.
