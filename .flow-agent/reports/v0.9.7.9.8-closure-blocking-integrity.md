# v0.9.7.9.8 Closure-Blocking Safety, Governance and Diagnostic Integrity

## Status

The bounded correction is `active`, parent Core item `0.9.7.9` is `correction-required`, and closure item `0.9.7.10` is `blocked` until the corrected implementation passes both exact-head and merge-candidate Flow CI validation.

## Why this correction exists

The preceding correction track repaired lowering, typed values, environment evidence, source polarity, provider-backed approval, collision-safe identity, derived report integrity, CLI rendering and release publication. A final audit still found closure-blocking gaps:

- arbitrary or vague text could still satisfy authored safety evidence;
- CI/CD bias health had previously depended on raw line substring matching;
- the public CLI selected Jenkins implicitly and delegated unknown commands to a legacy entrypoint;
- expected target incompatibility could escape as a stack trace;
- canonical topology could certify retained claims when independent source provenance was absent;
- legacy dependency projections lacked materialization-level equality checks;
- ordinary GitHub Actions dependency jobs used `always()`;
- GitHub pull-request merge refs were recorded as exact-head validation.

## Implemented boundaries

### Authored control evidence

`AuthoredControlEvidenceTextAuthority` classifies values as `CONFIRMED`, `DENIED` or `UNKNOWN`.

- boolean confirmation remains explicit;
- string confirmation is bounded to `true`, `yes` and `confirmed`;
- denial and unresolved markers are recognized inside longer text;
- generic words such as `available`, `complete`, `approved`, `required` and `policy` are not evidence;
- backup evidence requires a concrete locator or structured identifier;
- rollback evidence requires an action and a concrete rollback object or reference;
- change evidence requires a ticket identifier or URI;
- retention evidence requires a bounded duration;
- generic safety evidence must resolve to a concrete dry-run, backup, rollback, ticket or retention control.

Negative regression cases include `backup later`, `backup something`, `snapshot pending`, `rollback someday please`, `policy later` and `approval pending`.

### CI/CD bias governance

`CiCdBiasInventoryAnalyzer` performs bounded Kotlin lexical scanning and separates executable identifiers, control literals, ordinary strings, catalog declarations, comments, structured text and retained compatibility symbols. Only actionable coupling in active semantic source contributes to `healthStatus`.

### CLI target neutrality and diagnostic outcomes

The legacy `org.flowlang.cli.FlowCliKt` entrypoint is removed. The public CLI has one testable `runCli` boundary and one process `main`:

- no `--target` means target-neutral negotiation and selection evidence;
- `--render` requires an explicit target;
- expected target blockers produce `EXECUTABLE`, `REVIEW_ONLY` or `BLOCKED` outcomes;
- diagnostic manifest evidence remains printable and exportable;
- non-executable render requests emit `CLI_RENDER_NOT_AUTHORIZED` and write no target syntax;
- unknown commands and invalid input produce structured JSON diagnostics without stack traces.

### Canonical topology provenance

`ExecutionPlanCanonicalTopologyAuthority` derives canonical topology only from `sourceIntent`. Retained canonical requirements are never reused as expected values for their own validation.

`ExecutionPlanTopologyValidator` emits `planning.topology.canonical.provenance.missing` when an execution plan loses `sourceIntent` while retaining canonical requirements, lowering provenance or source-linked task nodes. Removing both the canonical claims and `sourceIntent` therefore cannot hide intent-derived topology.

The validator continues to reject missing, forged and orphaned canonical requirements before provider invocation.

### Retained derived projections

- `dependsOn` is the dependency authority;
- legacy `dependencies` is a serialized compatibility projection;
- typed `effectModel` is the effect authority;
- legacy `effects` is a resource-name projection.

`ExecutionPlanDerivedProjectionValidator` rejects dependency divergence recursively. Existing effect projection checks remain mandatory.

### GitHub Actions cancellation and validation identity

`GitHubJobConditionAuthority` preserves native GitHub cancellation semantics:

- ordinary dependent jobs emit no explicit condition;
- error handlers use `!cancelled() && failure()`;
- provider-backed approval skip evaluation uses `!cancelled()`;
- `always()` is not emitted for ordinary dependency jobs.

The standard Flow CI workflow now has two independent pull-request checks:

1. `compile-test-conformance` checks out `github.event.pull_request.head.sha`, verifies `git rev-parse HEAD`, and validates that exact revision.
2. `merge-candidate-compile-test-conformance` checks out GitHub's synthetic merge candidate, verifies its SHA, and runs the same repository, test and conformance boundaries.

A merge candidate may no longer be described as exact-head evidence.

## Public artifacts

The correction retains the schemas for:

- `target-neutral-planning-report.json`;
- `cli-target-outcome.json`;
- `target-render-readiness.json`.

No package, public-standard or existing artifact-contract version is advanced.

## Governance lifecycle

While the correction is active:

- the correction work package is the selected work item;
- parent Core item `0.9.7.9` is `correction-required`;
- Core closure item `0.9.7.10` is `blocked`;
- an active correction and a Core `next` item cannot coexist.

After one corrected implementation head passes both Flow CI jobs, a separate metadata-only head may:

- mark the work package `complete`;
- return `0.9.7.9` to `completed`;
- advance `0.9.7.10` to `next`;
- record the exact implementation and merge-candidate run evidence;
- pass the same dual CI boundary before the pull request becomes ready for review.

## Validation policy

The exact implementation head must pass:

- Flow Agent tooling tests;
- Flow Agent structure validation;
- Flow Agent context generation;
- clean Gradle compilation and complete tests;
- standalone conformance;
- existing executable reference evidence.

The synthetic merge candidate must independently pass the corresponding repository, test and conformance checks.
