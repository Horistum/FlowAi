# v0.9.7.9.8 Closure-Blocking Safety, Governance and Diagnostic Integrity

## Status

Implementation candidate assembled. The bounded correction remains `active`, parent Core item `0.9.7.9` remains `correction-required`, and closure item `0.9.7.10` remains `blocked` until exact-head Flow CI passes.

## Why this correction exists

The preceding correction track repaired lowering, typed values, environment evidence, source polarity, provider-backed approval, collision-safe identity, derived report integrity, CLI rendering and release publication. A final audit still found closure-blocking gaps:

- arbitrary non-empty text could satisfy authored safety evidence;
- CI/CD bias health was based on raw line substring matching and could flag its own catalog;
- the public CLI still selected Jenkins implicitly and delegated unknown commands to a legacy second entrypoint;
- expected target incompatibility could escape as a stack trace instead of producing diagnostic evidence;
- canonical workflow and capability topology could be omitted from an execution plan without independent re-derivation;
- legacy dependency projections remained without a materialization-level equality check;
- ordinary GitHub Actions dependency jobs used `always()` and could evaluate after workflow cancellation;
- the Core closure gate was marked next while these invariants were unresolved.

## Implemented boundaries

### Authored control evidence

`AuthoredControlEvidenceTextAuthority` classifies values as `CONFIRMED`, `DENIED` or `UNKNOWN`.

- explicit positive values are confirmed;
- explicit negative values are denied;
- placeholders and ambiguity remain unknown;
- backup references, rollback instructions, change-ticket identifiers, retention durations and concrete safety controls may be recognized through control-specific structure;
- arbitrary unrelated prose never becomes positive evidence merely because it is non-empty.

`CanonicalControlRequirementAuthority` uses this authority for backup, rollback, change-ticket, retention and generic safety parameters. The former blacklist-based `asConfirmedText` path is removed.

### CI/CD bias governance

`CiCdBiasInventoryAnalyzer` now performs bounded Kotlin lexical scanning.

It distinguishes:

- executable identifiers;
- control and default literals;
- ordinary string literals;
- catalog declarations;
- comments;
- structured non-Kotlin text.

Only actionable target/tool coupling in active semantic source contributes to `healthStatus`. Adapter vocabulary, application composition, documentation, scenarios and the analyzer's own catalog remain visible as inventory but do not manufacture a failing semantic-health verdict.

### CLI target neutrality and diagnostic outcomes

The legacy `org.flowlang.cli.FlowCliKt` entrypoint is removed.

The public CLI now exposes one testable `runCli` boundary and one process `main`:

- no `--target` means target-neutral negotiation and selection evidence;
- `--render` requires an explicit target;
- expected target blockers produce `EXECUTABLE`, `REVIEW_ONLY` or `BLOCKED` outcomes;
- diagnostic manifest evidence remains printable and exportable;
- non-executable render requests emit `CLI_RENDER_NOT_AUTHORIZED`, write no target syntax and return a non-zero command status;
- unknown commands and invalid input produce structured JSON diagnostics without a stack trace.

### Canonical topology provenance

`ExecutionPlanCanonicalTopologyAuthority` independently re-derives canonical topology from retained source metadata:

- workflow scope;
- workflow lifetime;
- approval suspend/resume requirements;
- failure propagation requirements.

The materialization validator rejects missing, forged and orphaned canonical requirements before provider invocation. It no longer validates the plan by calling the same topology derivation with an empty canonical input.

### Retained derived projections

The project makes an explicit governance decision for duplicate compatibility fields:

- `dependsOn` is the dependency authority;
- legacy `dependencies` is a serialized compatibility projection;
- typed `effectModel` is the effect authority;
- legacy `effects` is a resource-name projection.

`ExecutionPlanDerivedProjectionValidator` rejects dependency divergence recursively. Existing effect projection checks remain mandatory. The roadmap required outcome is updated from unconditional removal to explicit retained-and-enforced derivation.

### GitHub Actions cancellation

`GitHubJobConditionAuthority` owns job-level condition translation.

- ordinary dependent jobs emit no explicit condition and retain GitHub's native success/cancellation semantics;
- error handlers use `!cancelled() && failure()`;
- provider-backed approval skip evaluation uses `!cancelled()` and exact dependency results;
- `always()` is not emitted for ordinary dependency jobs.

## Public artifacts

Added schemas for:

- `target-neutral-planning-report.json`;
- `cli-target-outcome.json`;
- `target-render-readiness.json`.

The artifact bundle and contract index declare their roles, provenance and introduction in `0.9.7.9.8`.

## Governance lifecycle

Flow Agent now supports an explicit active bounded correction work package.

While the correction is active:

- the correction work package is the selected work item;
- parent Core item `0.9.7.9` is `correction-required`;
- Core closure item `0.9.7.10` is `blocked`;
- an active correction and a Core `next` item cannot coexist.

After the implementation candidate passes exact-head CI, a separate metadata-only head may:

- mark the work package `complete`;
- return `0.9.7.9` to `completed`;
- advance `0.9.7.10` to `next`;
- run a second exact-head Flow CI over the final governance state.

## Validation policy

The implementation candidate must pass, on one exact head:

- Flow Agent tooling tests;
- Flow Agent structure validation;
- Flow Agent context generation;
- clean Gradle compilation and complete tests;
- RC and snapshot checks;
- standalone conformance;
- existing executable reference evidence.

No package, public-standard or existing artifact-contract version is advanced by this correction.
