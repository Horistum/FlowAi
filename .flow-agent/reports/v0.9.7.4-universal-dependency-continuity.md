# v0.9.7.4 Universal Dependency and Continuity Contract

## Status

Completed.

## Objective

Distinguish execution ordering from value transfer, workspace continuity and state continuity so a target cannot claim materialization readiness merely because tasks appear in sequence.

## Implemented contract

- execution plans carry typed `ORDERING`, `VALUE`, `WORKSPACE` and `STATE` dependency relations
- every relation records its evidence source, resolution, path, candidates, continuity meaning and blocking status
- canonical module contracts declare continuity providers, requirements and preservation rules
- the planner resolves direct continuity and continuity preserved through compatible intermediate nodes
- missing and ambiguous continuity remains explicit blocking evidence rather than becoming an ordering assumption
- materialization authorization reloads the canonical module registry and rejects omitted, contradictory or forged continuity evidence
- diagnostic authorization preserves blockers while remaining explicitly non-executable
- target compatibility derives from declared continuity capabilities rather than renderer structure or task layout

## Reference evidence

The checkout-and-build reference proves a workspace path from `git.checkout` through `standard.execute` to `docker.build`. Jenkins retains supported workspace continuity. GitHub Actions is now honestly blocked because the target inventory does not represent an explicit workspace-transfer mechanism. That result is evidence about current target capability, not a change to Core meaning.
