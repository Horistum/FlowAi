# v0.9.7.9.10 Target Selection Provenance and CLI Status Integrity

## Status

The bounded correction is `active`. Parent Core item `0.9.7.9` is `correction-required`, and closure item `0.9.7.10` is `blocked`. No passing validation is claimed until the public pull-request head and its synthetic merge candidate independently pass Flow CI.

## Why this correction exists

A post-merge audit of the typed target-selection work found four related defects:

1. `CliTargetProjectionComposition.kt` still declared a dead `org.flowlang.cli.TargetManifestGenerationPipeline` facade while the live CLI used `org.flowlang.generators.manifest.TargetManifestGenerationPipeline`;
2. that dead facade derived a target from `CompatibilityReport` and relabeled it as `EXPLICIT_CONFIGURATION` with source `cli:compatibility-report`;
3. `TargetSelectionOrigin` lacked an exact closed-set guard, so a later `DEFAULT` or `FALLBACK` origin could be added without failing architecture validation;
4. CLI process status collapsed `REVIEW_ONLY` and `BLOCKED`, and successful results still accepted an independent exit-code parameter.

The facade was not on the live execution path, but it was compiled production code and a ready-made bypass pattern for the exact invariant the previous correction claimed to establish.

## Implemented boundary

### One production projection pipeline

- The dead CLI composition facade is deleted.
- Unit and standalone conformance check that `org/flowlang/cli/TargetManifestGenerationPipeline.class` is absent.
- The same checks require `org/flowlang/generators/manifest/TargetManifestGenerationPipeline.class` to remain present.

### Closed selection provenance

- Reference snapshots use `TargetSelectionAuthority.fromReferenceSnapshot`.
- Explicit configuration sources are represented by a closed vocabulary for reference snapshots, conformance checks and test fixtures.
- The transitional conformance compatibility adapter accepts only those declared categories and rejects every unknown prefix.
- `cli:compatibility-report` fails before an `ExplicitTargetSelection` can be issued.
- `TargetSelectionOrigin.entries` must remain exactly `CLI_OPTION`, `INTENT_DECLARATION` and `EXPLICIT_CONFIGURATION`.

### Derived CLI process status

- `CliProcessExit` defines success `0`, invalid input `2`, review required `3`, blocked `4` and internal error `70`.
- `REVIEW_ONLY` returns success only when evidence is inspected without a strict or render gate.
- A strict or render request over review-only evidence returns `REVIEW_REQUIRED`.
- `BLOCKED` always returns `BLOCKED`, including when rendering was not requested.
- `Completed` has no caller-supplied exit-code field.
- Rejected integrity and internal failures derive their process status from stable diagnostic codes.

## Explicit non-claim

The hard-coded retained compatibility symbol `KUBERNETES_MAINTENANCE` is not replaced by this correction. A manifest with package/public-standard expiry axes remains separate bounded governance work; this report does not disguise that remaining item as complete.

## Version boundary

The implementation package remains `0.9.5`, the public standard remains `0.8.0`, and the artifact contract remains `2.0`.

## Validation boundary

The implementation head must pass both Flow CI jobs:

- exact pull-request head;
- synthetic merge candidate.

After implementation evidence passes, completion metadata must be committed separately and the resulting head must pass the same two jobs before the pull request may become ready for review.
