# v0.9.6.6 Native Image Build Report

## Purpose

Add honest native `docker.build` projection coverage across selected built-in targets using typed bindings and the provider-owned architecture from v0.9.6.4.

## Implemented coverage

### Jenkins

- Payload: `JENKINS_STEP/docker-build`.
- Bindings: `image`, `context`, optional `dockerfile`, `push`.
- Uses the Docker Pipeline `docker.build()` object API and optional returned-image `push()` method.
- Supports the default Dockerfile for the selected context.
- Rejects a custom Dockerfile because Jenkins exposes that selection through a free-form Docker CLI argument string.

### GitHub Actions

- Payload: `GITHUB_ACTION/docker/build-push-action@v7`.
- Bindings: Flow image, path, optional Dockerfile and push policy to structured `tags`, `context`, `file` and `push` inputs.
- Uses the action's default Git context and maps a subdirectory to `{{defaultContext}}:<path>`.
- Requires a custom Dockerfile to remain inside the selected context and renders it relative to that context.

### Tekton

- Payload: `TEKTON_TASK/buildah` using the reviewed Catalog Task 0.9 contract.
- Bindings: `IMAGE`, `CONTEXT`, `DOCKERFILE`, `SKIP_PUSH` and a literal `source` workspace.
- Declares the Pipeline workspace and binds it to the Task's required `source` workspace.
- Inverts Flow `push` only at the concrete edge because the Task contract exposes `SKIP_PUSH`.

## Shared semantic contract

All selected targets preserve image identity, build context, Dockerfile selection and push policy. Context and Dockerfile are compile-time workspace-relative paths. Image values may interpolate declared Flow inputs through target-native input syntax.

Absolute, traversing, option-like, whitespace, control-character or dynamic paths fail closed. Unknown dollar interpolation and non-boolean push policy also fail closed.

No target syntax, Docker CLI command construction or path interpretation is added to Flow Core.

## Unsupported targets

Targets without both registry evidence and a provider-owned image-build contract remain `ADAPTER_REQUIRED` or review-only. Coverage is not inherited from another platform merely because both can eventually run a container builder.

## Tests

Coverage verifies:

- registry, provider catalog and renderer agreement for all three targets;
- parser, validator and planner carrying `docker.build` capability evidence;
- executable readiness through the real compatibility and manifest pipeline;
- dynamic image interpolation through Jenkins, GitHub Actions and Tekton native input syntax;
- default and explicit context, Dockerfile and push behavior;
- Jenkins fail-closed behavior for custom Dockerfiles requiring CLI arguments;
- GitHub context-relative custom Dockerfile enforcement;
- unsafe or dynamic path rejection;
- invalid push policy and unknown interpolation rejection;
- adapter-required behavior for an unimplemented target;
- canonical reference snapshot alignment after image-build capability and materialization changes.
