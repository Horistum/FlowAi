# v0.9.7.5 Canonical Intent Meaning

## Status

Completed.

## Objective

Separate inventory-independent intent meaning from explicit implementation binding so the same authored intent retains the same semantic identity regardless of which modules or targets are available.

## Implemented contract

- `CanonicalIntentMeaningAuthority.canonicalize` derives meaning without consulting a module registry
- canonical meaning includes standard capabilities, semantic parameters, dependencies, outputs, policies and failure semantics
- systems, `uses`, tools, engines and implementation action identities remain outside canonical meaning
- `resolve` produces separate `IntentBindingEvidence` without mutating canonical meaning
- every explicit `uses` declaration must resolve to exactly one module action, a declared compatible system and an action that explicitly implements the requested standard capability
- module descriptors expose implemented standard capabilities through the strict `implements` contract
- unbound standard capabilities lower to `standard.execute` semantic work rather than selecting git, Docker, Argo CD, Kubernetes or notification modules implicitly
- the semantic `target` parameter cannot be reused as an implicit system selector
- invalid binding evidence stops validation and cannot reach planning or materialization

## Compatibility and migration

Existing explicit bindings remain supported when their module action declares the corresponding standard capability and the intent selects a compatible system through `params.system`. Unbound intent remains valid but produces target-neutral semantic work. The migration guide documents the descriptor and intent changes required for explicit binding.

## Reference evidence

Both reference snapshot directories were regenerated through `ReferenceSnapshotBundleGenerator`. The checkout-and-build executable proof remains live, while the mixed deployment reference reflects the new standard failure-notification semantics without inventing implementation support.

## Boundary

This work does not add runtime execution, target-specific public syntax, a preferred implementation inventory or implicit binding defaults. Package version `0.9.5`, next package line `0.9.6`, public standard version `0.8.0` and artifact contract version `2.0` remain unchanged.
