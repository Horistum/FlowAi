# v0.9.7.10 Bounded Semantic Closure Gate

## Status

The closure work package is `active` in the explicit `READY` phase. A first real `CLOSED` metadata candidate was rejected by Flow CI #2169 because an older closure-blocking conformance check permanently required `closureStatus: next` after correction completion. The metadata claim was removed and the invariant was repaired at its owner. A new implementation head and synthetic merge candidate must pass before closure can be marked complete again.

## Purpose

Close the v0.9.7 universal semantic foundation by reconciling only evidence already declared by the roadmap, release profile, correction work packages and conformance runner. The gate introduces no new semantic requirement while evaluating closure.

## Finite checklist

The work package and `SemanticClosureAuthority.CHECKLIST` match exactly and in order. Adding, removing or reordering an item makes closure fail.

## Execution ordering

`SemanticClosureChecks` is the final conformance group. It receives an immutable snapshot of checks that already ran. It cannot certify a later check, lend evidence to itself or turn a failed prior check into a successful aggregate result.

## Explicit release lifecycle

`ReleaseMetadataHonestyAuthority` models two valid closure phases:

- `READY`: the latest bounded correction is complete, the closure work package is active, the Core track is active, item `0.9.7.10` is next and the latest completed Core item remains `0.9.7.9`.
- `CLOSED`: the closure work package is complete, the Core track and item `0.9.7.10` are completed, the latest completed Core item is `0.9.7.10`, and the work package contains structured passing implementation evidence with distinct exact-head and merge-candidate SHAs.

Every mixed state is `INVALID` and fails release metadata honesty. A completed work package without a positive Flow CI run number and id, exact head, merge candidate or distinct SHAs also fails.

The release metadata report contract is version `1.3`. Its JSON schema exposes closure item, closure work-package status, closure phase, Core track status and latest completed Core item, and permits `closureStatus: completed`.

## Closure-blocking conformance repair

The first `CLOSED` candidate proved that `ClosureBlockingIntegrityChecks.checkCorrectionLifecycle` still encoded an obsolete transition rule:

- correction `complete` implied closure status must remain `next` forever.

That rule was valid only before closure. It has been replaced by `checkReleaseLifecycle`, which consumes the validated release report and checks the complete phase combination:

- `READY`: correction complete, parent completed, closure work package active, closure item next, Core track active and completed item `0.9.7.9`;
- `CLOSED`: correction complete, parent completed, closure work package complete, closure item completed, Core track completed and completed item equal to the closure identity;
- any `INVALID` phase fails.

The repair does not independently permit either status. It removes a second lifecycle authority and delegates phase truth to `ReleaseMetadataHonestyAuthority`.

## Completed-track tooling

Flow Agent validation and context generation understand a structurally completed primary track. A completed track must contain no next item, declare track status completed, retain no active correction pointer, identify the closure item as completed and contain no incomplete Core item. A missing next item on an active or incomplete track remains an error.

## Negative evidence

Unit and standalone conformance tests prove that closure or release honesty fails when:

- one required release check is absent;
- a non-release-profile check fails;
- a bounded correction is reactivated;
- the declared checklist diverges from the authority;
- closure is complete without structured implementation evidence;
- a completed closure leaves the Core track active;
- completed metadata still points to `0.9.7.9`;
- an active closure publishes a completed roadmap status;
- a primary track has no next item but is not structurally completed.

The lifecycle fixtures normalize their source metadata explicitly, so the same negative cases remain valid before and after repository closure.

## Validation history

Flow CI #2163 passed the lifecycle authority, schema, negative fixtures and completed-track tooling before the first metadata transition.

Flow CI #2169 then rejected the first real `CLOSED` candidate:

- exact and merge-candidate Flow Agent tooling accepted the structurally completed track;
- merge-candidate full tests failed `governance.closure-blocking-safety-diagnostic-integrity`;
- the final semantic closure check also failed because it correctly retained that prior conformance failure;
- the completion claim was reopened rather than waived.

## Current validation boundary

The repaired implementation must now independently pass:

- exact-head Flow CI;
- synthetic merge-candidate Flow CI;
- complete tests;
- standalone conformance.

Only after that implementation evidence exists may a later metadata head restore `CLOSED` and pass the same dual boundary again.
