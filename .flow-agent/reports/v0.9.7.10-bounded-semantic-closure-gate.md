# v0.9.7.10 Bounded Semantic Closure Gate

## Status

The closure work package is `active` in the `READY` phase. The Core roadmap item remains `next` until the finite closure authority and the extended release-metadata lifecycle pass on an exact pull-request head and synthetic merge candidate. No completion claim is made before that evidence exists.

## Purpose

Close the v0.9.7 universal semantic foundation by reconciling only evidence already declared by the roadmap, release profile, correction work packages and conformance runner. The gate may not introduce a new semantic requirement while evaluating closure.

## Finite checklist

1. `closure.checklist-exact`
2. `closure.no-active-corrections`
3. `closure.prior-core-items-complete`
4. `closure.release-metadata-honest`
5. `closure.required-checks-present`
6. `closure.required-checks-pass`
7. `closure.no-failed-conformance`
8. `closure.version-boundary-unchanged`
9. `closure.reference-evidence-live`

The work package and `SemanticClosureAuthority.CHECKLIST` must match exactly and in order. Adding, removing or reordering an item makes closure fail.

## Execution ordering

`SemanticClosureChecks` is the final conformance group. It receives an immutable snapshot of checks that already ran. It cannot certify a later check, and it cannot turn a failed prior check into a successful aggregate result.

## Explicit release lifecycle

`ReleaseMetadataHonestyAuthority` now models two valid closure phases:

- `READY`: the latest bounded correction is complete, the closure work package is active, the Core track is active, item `0.9.7.10` is next and the latest completed Core item remains `0.9.7.9`.
- `CLOSED`: the closure work package is complete, the Core track and item `0.9.7.10` are completed, the latest completed Core item is `0.9.7.10`, and the work package contains structured passing implementation evidence with distinct exact-head and merge-candidate SHAs.

Every mixed state is `INVALID` and fails release metadata honesty. A completed work package without a positive Flow CI run id, exact head, merge candidate or distinct SHAs also fails.

The release metadata report contract is version `1.3`. Its schema exposes the closure work-package status, closure phase, Core track status and latest completed Core item, and accepts `closureStatus: completed` only as part of a report that may still independently be `FAIL` when another axis disagrees.

## Completed-track tooling

Flow Agent validation and context generation now understand a structurally completed primary track. A completed track must:

- contain no `status: next` Core item;
- declare track status `completed`;
- retain no active correction pointer;
- identify the same closure item as both the completed Core item and bounded closure identity;
- contain no incomplete Core item.

The fallback is not permissive. A missing next item on an active track remains an error.

## Fail-closed boundaries

- Any active `0.9.7.9.x` bounded correction blocks closure.
- Any incomplete Core item from `0.9.7.1` through `0.9.7.9` blocks closure.
- Any missing release-profile check blocks closure.
- Any failed required or non-required prior conformance check blocks closure.
- Release metadata honesty must pass independently.
- Package `0.9.5`, public standard `0.8.0` and artifact contract `2.0` must remain unchanged.
- Behavioral generator equivalence, reference intent corpus and executable corpus harness must still be present and passing.

## Negative evidence

Unit tests prove that closure or release honesty fails when:

- one required release check is absent;
- a non-release-profile check fails;
- a bounded correction is reactivated;
- the declared checklist diverges from the authority;
- closure is complete without structured implementation evidence;
- a completed closure leaves the Core track active;
- completed metadata still points to `0.9.7.9`;
- an active closure publishes a completed roadmap status;
- a primary track has no next item but is not structurally completed.

## Validation boundary

The implementation head and a later completion-metadata head must each pass:

- exact-head Flow CI;
- synthetic merge-candidate Flow CI;
- complete tests;
- standalone conformance.
